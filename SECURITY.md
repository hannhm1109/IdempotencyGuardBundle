# Security policy

## Supported scope

The initial release line is 0.1.x on PHP 8.1+ and Symfony 6.4. Use the latest patch dependencies supported by your PHP runtime and inspect the repository's CI status before upgrading. Symfony 7/8 support is not declared. No support duration or independent security audit is promised by this repository.

## Boundaries that affect correctness

- This bundle coordinates one host with Symfony FlockStore. Every worker/release must use the same supported lock directory and replay pool. A shared cache alone does not coordinate multiple hosts.
- A business effect and its response record are not a transaction. Crashes, failed persistence, eviction, cache clearing, and expiry can allow re-execution. Retain database uniqueness/transactional safeguards and external-provider idempotency where required.
- PSR-6 pools can hide read failures as misses. Fail-closed handling applies to failures actually reported to the bundle, not failures hidden by the cache backend.
- Authenticate and authorize before replay through Symfony security rules/attributes. Checks only inside the controller do not run on replay. Custom controller-argument access listeners must precede priority -256.
- Keys are scoped by origin/base path and authenticated user class, identifier, and firewall when available. User identities/classes must be stable and globally unique within that scope. Tenant-local identities require an application-specific scope design before using private tenant responses. Anonymous callers share a scope; private anonymous responses are unsuitable.
- Request payloads are hashed, not stored. Hashes are not encryption or anonymization. Response bodies and allowlisted Location/Content-Type headers are stored and can contain personal data. Keep passwords, secrets, and access tokens out of responses; use a trusted, access-controlled cache with deliberate retention. Cache serialization assumes trusted backend data.
- Controllers must return supported full buffered responses. Unsupported response types are not recorded, so retries can execute again. A snapshot over 1 MiB or a failed save returns an uncertain 500 after execution.
- Body/status/cache-policy transformations must run before the response subscriber at priority -1024. Exceptions after a successful snapshot trigger deletion while the lock is held; cleanup/backend failure can still leave an uncertain record. An arbitrary late listener mutating a successful response without throwing is outside the contract.
- A standalone HttpKernel should catch all Throwables if custom view/response listeners can throw PHP Errors. The bundle wraps controller Throwables, but cannot catch an Error outside that callable when the kernel itself refuses to handle it. Symfony application kernels normally handle this lifecycle.
- Configure trusted hosts/proxies in the application. Set request limits upstream; PHP may buffer input before the bundle's 1 MiB limit runs. Use sufficiently unpredictable operation keys and keep the same key only for retries of the same operation.
- Generic bundle infrastructure logs contain only an exception class. Application/backend logs, cookies regenerated by listeners, and the surrounding authentication system have separate privacy responsibilities.

## Reporting

If GitHub's private vulnerability reporting is enabled for this repository, use its **Security → Report a vulnerability** flow. Otherwise contact [the maintainer](https://github.com/hannhm1109) to request a private reporting channel without posting exploit details or sensitive data in a public issue. Do not include real credentials, production response bodies, or personal data in a report. This policy does not claim private reporting is enabled or promise a response time.
